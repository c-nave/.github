# PR 가이드

> **왜 PR 을 강제하는가**
> PR 은 "코드를 합쳐도 되는지 검증하는 절차"이자 **변경의 맥락을 남기는 유일한 지점**입니다.
> 커밋은 "무엇을 했는지"만 남지만, PR 은 "무엇을 검토했고 왜 이렇게 합의했는지"가 남습니다.
> 1인 프로젝트라도 PR 을 거치면 나중에 `git blame` → 커밋 → PR → 이슈 순으로 맥락을 되짚을 수 있습니다.

---

## 1. PR 을 올리기 전 체크리스트

- [ ] 대상 브랜치가 맞다 (`feature/*` → `develop`, `release|hotfix/*` → `main`)
- [ ] 최신 `develop` 을 반영했다 (`git rebase origin/develop`)
- [ ] 로컬에서 빌드와 테스트가 통과한다
- [ ] 디버그 코드, 주석 처리된 코드, `console.log` / `print` 를 지웠다
- [ ] 비밀값(API 키, 비밀번호, 인증서, `.env`)이 들어가지 않았다
- [ ] 연결된 이슈가 있다

---

## 2. PR 제목

**커밋 컨벤션과 동일한 형식**을 씁니다. Squash merge 시 이 제목이 그대로 커밋 메시지가 되기 때문입니다.

```
feat(export): CSV 내보내기 추가
fix(auth): 토큰 만료 시 무한 리다이렉트 수정
chore(deps): axios 1.7.2 로 업데이트
```

작업이 아직 안 끝났으면 **Draft PR** 로 올립니다. 제목에 `[WIP]` 를 붙이지 마세요.
Draft 상태는 GitHub 이 이미 표시해 주고, 머지 버튼도 자동으로 잠깁니다.

---

## 3. PR 본문에 반드시 들어갈 것

템플릿([`.github/PULL_REQUEST_TEMPLATE.md`](../.github/PULL_REQUEST_TEMPLATE.md))이 자동으로 채워집니다.

| 항목 | 왜 필요한가 |
|---|---|
| **관련 이슈** | `Closes #12`. 이슈-PR-커밋이 이어져야 나중에 추적이 됨 |
| **변경 사항** | 리뷰어가 diff 를 열기 **전에** 무엇을 볼지 알게 함 |
| **왜 이렇게 했는지** | 대안을 검토하고 버린 이유. diff 에는 절대 안 남는 정보 |
| **테스트 방법** | 리뷰어가 직접 확인할 수 있는 재현 절차 |
| **스크린샷 / 로그** | UI 변경이거나 동작 변화가 있으면 필수 |
| **영향 범위·주의사항** | 마이그레이션 필요, 설정 추가, 배포 순서 의존성 등 |

---

## 4. PR 크기

**변경 라인 400줄 이내를 목표로 합니다.**

리뷰 품질은 PR 크기에 반비례합니다. 1,000줄짜리 PR 은 사실상 "LGTM" 도장만 받고 지나갑니다.

| 규모 | 대응 |
|---|---|
| ~200줄 | 이상적. 리뷰 30분 이내 |
| 200~400줄 | 정상 범위 |
| 400~800줄 | 쪼갤 수 있는지 먼저 검토. 불가하면 PR 본문에 이유를 적는다 |
| 800줄+ | **쪼갠다.** 리팩토링 PR 과 기능 PR 을 분리하는 것만으로 대부분 해결됨 |

**쪼개는 방법**

- 리팩토링 → 기능 추가 → 테스트 순으로 PR 을 나누고, 앞 PR 을 base 로 스택을 쌓는다
- 자동 생성 파일(lock 파일, 마이그레이션, 빌드 산출물)은 별도 커밋으로 분리해 리뷰어가 건너뛰게 한다

---

## 5. 리뷰어 지정

| 상황 | 리뷰어 |
|---|---|
| 일반 기능·수정 | 해당 저장소 담당자 1명 이상 |
| 아키텍처·공용 모듈 변경 | 담당자 + 다른 파트 1명 |
| 배포 스크립트·인프라·CI | 인프라 담당 필수 |
| 1인 저장소 | 셀프 머지 가능하되, PR 본문은 동일하게 작성 |

`CODEOWNERS` 를 두면 경로별로 리뷰어가 자동 지정됩니다.

```
# .github/CODEOWNERS
*                       @팀리드
/infra/                 @인프라담당
/src/core/              @코어담당
*.sql                   @DB담당
```

## 6. 리뷰 규칙

### 리뷰어

- **24시간 이내에 응답**합니다. 당장 볼 수 없으면 "언제 보겠다"라도 남깁니다.
- 코멘트는 **심각도를 접두어로 표시**합니다. 이게 없으면 사소한 취향 지적이 머지를 막습니다.

  | 접두어 | 의미 | 머지 차단 |
  |---|---|---|
  | `[must]` | 반드시 고쳐야 함 (버그, 보안, 규칙 위반) | O |
  | `[should]` | 고치는 게 좋음. 합의되면 다음 PR 로 미뤄도 됨 | △ |
  | `[nit]` | 취향·사소한 제안 | X |
  | `[question]` | 이해가 안 돼서 묻는 것 | X |
  | `[praise]` | 좋은 부분 언급 | X |

- **사람이 아니라 코드**를 지적합니다. "왜 이렇게 짰어요?" 대신 "이 경우 null 이 들어오면 어떻게 되나요?"
- 지적만 하지 말고 **대안이나 근거**를 함께 씁니다.

### 작성자

- 모든 코멘트에 **반응**합니다. 반영했으면 반영 커밋을 링크하고, 안 할 거면 이유를 답니다.
- 리뷰 지적을 반영한 커밋은 **강제 푸시하지 않습니다.** 리뷰어가 "무엇이 바뀌었는지" 볼 수 없게 됩니다.
  (머지 시 어차피 squash 되므로 정리할 필요가 없습니다)
- 반영이 끝나면 `Re-request review` 로 리뷰어에게 다시 요청합니다.

### 승인

- `Approve` 는 "내가 이 코드에 대해 함께 책임진다"는 뜻입니다. 안 읽었으면 누르지 않습니다.
- 이해가 안 되는 부분이 남았으면 `Approve` 대신 `Comment` 로 질문합니다.

## 7. 머지

| 대상 | 방식 |
|---|---|
| `feature/*` → `develop` | **Squash and merge** |
| `release/*`, `hotfix/*` → `main` | **Create a merge commit** |

**머지 조건**

- [ ] 승인 1개 이상
- [ ] CI 통과
- [ ] `[must]` 코멘트 전부 해소
- [ ] 충돌 없음

**머지는 작성자가 합니다.** 리뷰어가 대신 머지하면 작성자가 배포 타이밍을 통제할 수 없습니다.
머지 후 브랜치는 삭제합니다(자동 삭제 설정 권장).

## 8. 특수한 경우

### 긴급 배포 (핫픽스)

절차를 건너뛰지 않습니다. 대신 **리뷰를 동기로 전환**합니다 — 채널에 바로 멘션하고 화면 공유로 같이 봅니다.
사후에 PR 본문에 "긴급 배포 사유"와 "동기 리뷰 참여자"를 기록합니다.

### 되돌리기

배포 후 문제가 생기면 **먼저 되돌리고 원인을 찾습니다.**

```bash
# GitHub PR 화면의 Revert 버튼 사용 (되돌리기 PR 이 자동 생성됨)
# 또는
git revert -m 1 <머지커밋해시>
```

### 의존성 자동 PR (Dependabot 등)

- 패치 버전 업데이트는 CI 통과 시 승인 후 머지
- 마이너·메이저는 변경 로그를 확인하고 담당자가 판단
