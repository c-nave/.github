# 이슈 가이드

> **왜 이슈부터 쓰는가**
> 이슈는 **작업의 시작점이자 단위**입니다. 이슈 → 브랜치 → 커밋 → PR 이 번호로 연결돼야
> "이 코드가 왜 들어갔나"를 역추적할 수 있습니다.
> 또한 이슈를 쓰다 보면 "이건 사실 세 가지 작업이네" 를 **코드를 짜기 전에** 알게 됩니다.

**원칙: 이슈 없이 브랜치를 파지 않습니다.** (오타 수정 같은 사소한 변경은 예외)

---

## 1. 이슈 종류

| 종류 | 언제 | 템플릿 |
|---|---|---|
| 🐞 **버그** | 의도한 대로 동작하지 않음 | `bug.yml` |
| ✨ **기능 요청** | 새 기능·개선 제안 | `feature.yml` |
| 🔧 **작업** | 리팩토링, 문서, 빌드, 조사 등 | `task.yml` |

이슈를 열면 템플릿이 자동으로 뜹니다. 항목을 지우지 말고 채우세요.

---

## 2. 이슈 제목

**한 줄만 읽고도 무슨 일인지 알 수 있어야 합니다.**

| 나쁨 | 좋음 |
|---|---|
| `안 됨` | `로그인 후 새로고침하면 세션이 풀림` |
| `개선 필요` | `목록 조회가 5,000건 넘으면 10초 이상 걸림` |
| `CSV` | `조회 결과를 CSV 로 내보내는 기능 추가` |

- 접두어(`[BUG]` 등)는 붙이지 않습니다. **라벨이 그 역할**을 합니다.
- 한국어로 씁니다.

---

## 3. 버그 이슈에 반드시 들어갈 것

이 세 가지가 없으면 재현이 안 되고, 재현이 안 되면 고칠 수 없습니다.

1. **재현 절차** — 1, 2, 3 번호를 매겨 구체적으로
2. **기대 동작 / 실제 동작** — 둘 다 씁니다. "잘못 나옴" 은 정보가 아닙니다
3. **환경** — 버전, OS, 브라우저/런타임, 접속 경로

여기에 **로그·스크린샷·에러 메시지 전문**을 붙이면 해결 속도가 몇 배 빨라집니다.
로그는 스크린샷 말고 **텍스트로** 붙여 넣으세요. 검색이 됩니다.

```
# 나쁜 버그 리포트
"파일 내보내기 하면 에러남"

# 좋은 버그 리포트
제목: 5,000건 이상 조회 후 CSV 내보내기 시 타임아웃

재현 절차
1. 조회 화면에서 기간을 1년으로 설정
2. 조회 (결과 6,412건)
3. [CSV 내보내기] 클릭

기대: CSV 파일이 다운로드된다
실제: 30초 후 "요청 시간이 초과되었습니다" 토스트, 파일 없음

환경: v1.4.2 / Windows 11 / Chrome 126
로그:
  2026-07-20 14:03:11 ERROR ExportService - export timeout after 30000ms
  ...
```

## 4. 라벨 체계

라벨은 **종류 / 우선순위 / 상태 / 영역** 4개 축으로 나눕니다.
축마다 접두어를 붙여 정렬과 필터가 쉽도록 합니다.

### 종류 (`type:`) — 필수, 1개

| 라벨 | 색 | 의미 |
|---|---|---|
| `type: bug` | `#d73a4a` | 버그 |
| `type: feature` | `#0e8a16` | 새 기능 |
| `type: refactor` | `#1d76db` | 구조 개선 |
| `type: docs` | `#0075ca` | 문서 |
| `type: chore` | `#cfd3d7` | 빌드·설정·의존성 |
| `type: question` | `#d876e3` | 질문·논의 |

### 우선순위 (`P`) — 필수, 1개

| 라벨 | 색 | 기준 | 대응 |
|---|---|---|---|
| `P0: urgent` | `#b60205` | 서비스 중단, 데이터 손실 | 즉시. 핫픽스 |
| `P1: high` | `#d93f0b` | 핵심 기능 불가, 우회 수단 없음 | 이번 스프린트 |
| `P2: normal` | `#fbca04` | 불편하지만 우회 가능 | 다음 릴리스 |
| `P3: low` | `#c2e0c6` | 있으면 좋음 | 여유 있을 때 |

### 상태 (`status:`) — 선택, 필요할 때만

| 라벨 | 색 | 의미 |
|---|---|---|
| `status: blocked` | `#000000` | 다른 작업·외부 응답 대기로 진행 불가 |
| `status: need-info` | `#fef2c0` | 작성자에게 추가 정보 요청함 |
| `status: wontfix` | `#ffffff` | 의도된 동작이거나 고치지 않기로 결정 |
| `status: duplicate` | `#cfd3d7` | 중복 이슈 |

### 영역 (`area:`) — 선택, 저장소마다 정의

`area: api`, `area: ui`, `area: infra`, `area: db` 처럼 저장소 구조에 맞게 만듭니다.
저장소가 작으면 **만들지 않습니다.** 안 쓰는 라벨은 노이즈입니다.

### 기타

| 라벨 | 색 | 의미 |
|---|---|---|
| `good first issue` | `#7057ff` | 신규 합류자가 시작하기 좋은 작업 |

### 라벨 일괄 적용

저장소마다 손으로 만들지 말고 스크립트를 돌립니다.

```bash
# scripts/sync-labels.sh <org>/<repo>
bash scripts/sync-labels.sh c-nave/my-repo
```

## 5. 이슈 → 브랜치 → PR 연결

```
이슈 #42 "조회 결과를 CSV 로 내보내는 기능 추가"
  └─ 브랜치  feature/42-csv-export
       └─ 커밋   feat(export): CSV 내보내기 추가
            └─ PR   feat(export): CSV 내보내기 추가
                     본문에 "Closes #42"  →  머지 시 이슈 자동 종료
```

GitHub 이슈 화면 우측 **Development → Create a branch** 를 쓰면
이슈 번호가 포함된 브랜치가 자동 생성되고 이슈에 연결됩니다.

## 6. 이슈 운영 규칙

### 담당자(Assignee)

- 작업을 **시작할 때** 자기 자신을 assign 합니다. 미리 찜해두지 않습니다.
- 담당자가 없는 이슈 = 아무도 안 하고 있는 이슈. 이게 정확해야 백로그가 의미를 가집니다.

### 마일스톤

릴리스 버전(`v1.2.0`)을 마일스톤으로 만들고, 그 릴리스에 넣을 이슈를 붙입니다.
릴리스 노트를 쓸 때 마일스톤 하나만 보면 됩니다.

### 닫는 시점

- 버그 → **수정이 배포된 시점**. 머지만으로 닫지 않는 게 원칙이지만,
  `Closes` 로 자동 종료된 경우 배포 후 확인 코멘트를 남깁니다.
- 기능 → 머지 시점
- 논의 → 결론을 코멘트로 남기고 닫습니다. **결론 없이 닫지 않습니다.**

### 오래된 이슈

분기마다 3개월 이상 움직임 없는 이슈를 훑고, 아직 유효한지 판단해
`P3` 으로 내리거나 `status: wontfix` 로 닫습니다. 쌓인 백로그는 아무도 안 봅니다.

---

## 7. 이슈를 쪼개는 기준

아래에 해당하면 쪼갭니다.

- 완료 조건을 한 문장으로 못 쓴다
- 예상 작업량이 3일을 넘는다
- 담당자가 2명 이상 필요하다
- PR 이 400줄을 넘을 게 확실하다

큰 덩어리는 **부모 이슈 1개 + 자식 이슈 N개**로 만들고, 부모 본문에 체크리스트를 둡니다.

```markdown
## 하위 작업
- [ ] #43 내보내기 API 엔드포인트 추가
- [ ] #44 프론트 내보내기 버튼·진행률 UI
- [ ] #45 대용량 스트리밍 처리
```
